Part A · Orientation · Lesson 1

The big picture

What the project tests, the four tests it compares, and which script runs at each stage. There is no code in this lesson; it is the map the rest of the course fills in.

About 12 minutes · Sources: README.md, reports/proposal.md, reports/preregistration.md

1.1The question

Train a small model on Othello move lists, with no board and no rules, and it learns to propose legal moves. Has it built an internal picture of the board (a world model), or has it learned move statistics that happen to work?

Published papers answer with four different tests, and each paper picks its own. Nobody had run all four on the same models to see whether they agree. WM-Concord does exactly that: it trains a zoo of small models in worlds where the truth is known, runs all four tests on every model, and asks four questions.

  • H1Agreement. Do the four tests rank the models in the same order?
  • H2Disagreement. Where they disagree, is it systematic (tied to architecture, scale or training data) or noise?
  • H3Prediction. Which test best predicts a model breaking on shifted positions, measured by the fragility suite?
  • H4Generalization. Do the answers hold on a domain kept out of all earlier analysis (the interpreter)?
Why any outcome counts

If the tests agree, the cheap ones can stand in for the expensive ones. If they disagree, a paper that rests on one test is on weaker ground than it looks. The study reports either result.

1.2Why Othello: every move has an answer key

In Othello a move list fixes the board completely. For any position in any game, the rules can say what the board is and which moves are legal, so every test has an exact answer key to check the model against. New to the game? Lesson 2 teaches it in ten minutes.

The model’s input is tokens. The 60 squares a move can land on are tokens 1 to 60 (the four centre squares start occupied and are never played), and 0 is padding. The opening D3, C3, C4 reaches the model as 20 19 27.

All of this lives in one file, src/domains/othello.py. The trainer, all four tests, the fragility suite and the test suite import it, and no other file keeps its own copy of the rules. Lesson 3 opens it up.

Othello is the first of three planned domains. Navigation (street maps) and a small program interpreter come after 20 October; the interpreter is held out for H4.

1.4The pipeline: which script runs at each stage

The work runs as a chain of stages. Each stage is a script that reads files an earlier stage wrote, so any stage can be stopped, restarted or rerun on its own. One line matters more than the rest: no zoo model may be scored until the analysis rules are written down and tagged in git.

How Othello is played

Everything about the game you need to follow the code: the board, the opening, how a move flips discs, passing, and how a game ends. Then play a few moves yourself.

About 10 minutes · No code

2.1The board and the opening

Othello is played by two players, Black and White, on an 8 by 8 board. All the discs are the same: black on one side, white on the other. Columns are lettered A to H and rows numbered 1 to 8, so every square has a name such as D3. In this repo row 1 is at the top, so A1 is the top-left corner (square 0 in the code) and H8 the bottom-right (square 63).

Every game starts from the same four discs in the centre: White on D4 and E5, Black on E4 and D5. Black moves first.

2.2A move: trap and flip

A move puts one disc, your colour up, on an empty square. It is legal only if it traps at least one opponent disc: in a straight line from the new disc (across, up or down, or diagonal) there must be one or more opponent discs and then one of your own. Every trapped disc flips to your colour. If the new disc traps lines in several directions, all of them flip.

The four moves below are the opening used throughout this course.

2.3Passing and the end of the game

If the player to move has no legal move, they pass and the other player moves again. The game ends when neither player can move, almost always because all 64 squares are full after 60 moves. The player with more discs wins.

In the project’s test data, 98.8% of the random (synthetic) games and 96% of the championship games run the full 60 moves. Passes are not rare: about a third of the random games and 58% of the championship games contain at least one, and in random games the pass often comes just before the final move. A position offers about 8.5 legal moves on average.

Why passes matter to the code

The game files store only the squares played, never the passes. So when one player moves twice in a row, the code has to work out that the other player passed. Lesson 3 shows how replay() does it.

2.4Try it

The dots always show the legal moves for whoever is to move. Point at a dot to see which discs it would flip, then click to play it. Random move picks uniformly among the legal moves, which is exactly how the synthetic training games were made.

2.5Why Othello suits this project

  • The truth is exact.The rules are fixed and nothing is random, so a move list determines the board completely. That gives every test its answer key.
  • The board is hidden inside the move list.Which squares are occupied is easy: discs are never removed, so a square stays occupied once it has been played. Whose disc sits there is hard, because it depends on every flip since. This is why the project’s tests ask about ownership, and why D4 reports an occupancy-only baseline.
  • Mine and theirs.The code describes each board two ways: black / white, and mine / theirs relative to the player who just moved. Nanda et al. (2023) found Othello-GPT stores the board the second way: a linear probe reads mine / theirs at about 99%, but black / white at only about 75%. The team reproduced this before building on it (Lesson 13).
  • Strategy doesn’t matter, but it shapes the data.The models only learn which moves are legal, not how to win. Championship players do try to win, so their games look different from random ones, and that difference is one of the shifts the fragility suite tests (Lessons 4 and 14).

3.2Squares and tokens

  • 51–53The board is a NumPy array of 64 small integers: 0 empty, 1 black, 2 white. Square s sits at row s // 8, column s % 8.
  • 54The 8 directions a line can run in, as (row step, column step).
  • 55–56The four centre squares start occupied, so only 60 squares can ever be played.
  • 57–58Two lookup tables, square → token and back. Tokens number the 60 playable squares 1 to 60, in square order.
  • 59–6161 tokens in all, because 0 is padding. A game has at most 60 moves, and models read at most 59.

3.3The rules in three functions

Lesson 2’s rule, “trap at least one opponent disc in a straight line”, is flips_for(). The other two functions are built on it. (start_board(), just above, places the four opening discs.)

  • 90–91A square that is already taken can never be played.
  • 92–94Set up: who the opponent is, and the square’s row and column.
  • 95–99For each direction, step away from the square while the discs belong to the opponent, collecting them in line.
  • 100–101If the walk stopped on the player’s own disc (and is still on the board), the whole line is trapped: add it to the flips.
  • 105–107legal_moves(): every playable square where flips_for() is not empty.
  • 110–113legal_next(): after mover moved, the other player goes next if they can; if not, they pass and mover goes again; an empty list means the game is over. The pass rule is the single or on line 113.

3.4replay(): whole games, passes included

The data stores each game as the squares played and nothing else. replay() rebuilds the board after every move, and works out the passes the files never record.

  • 120–121Start from the opening with Black to move, and collect a board and a mover per move.
  • 124–127If the player to move cannot make the recorded move, that player must have passed: switch players and try again.
  • 128–129If neither player can make it, the record is broken: return None. Callers drop such games (the count is expected to be 0, and so far it always is).
  • 130–134Flip the trapped discs, place the new one, remember the board and the mover, hand the turn over.
  • 135Return the boards, shape (T, 64), and the movers, shape (T,).
The same rules, run forwards

play_random_game() (lines 138–157) plays a game instead of replaying one: at each turn it picks a legal move uniformly at random, passes when it must, and stops when neither player can move. The tests use it to make games anywhere, without the data; the board in Lesson 2 does the same when you press Random move.

4.4Championship games: the WTHOR format

A WTHOR file starts with a 16-byte header, then one 68-byte record per game. The header’s bytes 4 to 7 hold the number of games; the rest (creation date, year, board size) is not needed. In each record, the first 8 bytes describe the game (tournament, the two players, the scores) and the last 60 are the moves, one byte each, written as 10 × row + column with both counted from 1. 6.2Three architectures behind one shape

The diagnostics must never care which architecture they score. So every model class offers the same three methods: layer_outputs(x) returns the vector after each layer, readout(h) turns a last-layer vector into 61 next-move scores, and forward(x) is simply readout(layer_outputs(x)[-1]). That last line guarantees that the vectors D4 probes are exactly the vectors the model predicts from.

  • 77–78Each token gets a learned embedding plus a learned position embedding for positions 0 to 58: attention alone has no sense of order.
  • 79–83N standard PyTorch encoder layers: feed-forward width 4 × d_model, no dropout, GELU, and norm_first=True (pre-norm, as in GPT-2).
  • 90–96The causal mask lets position t attend only to positions 0 to t, so a prediction never sees the move it is predicting. The output after every block is collected.
  • 98–102readout applies a final LayerNorm and the linear head; forward is readout of the last block.
  • 105–108One nn.LSTM(num_layers=N) would compute the same thing but only return the last layer. A stack of single-layer LSTMs makes every layer reachable for D4. (Checkpoints of the earlier multi-layer version no longer load, which is why some LSTMs were retrained.)
  • 117–124No position embedding: the recurrence itself carries the order. The hidden state after each layer is collected.
  • 134–135The fast mamba_ssm CUDA kernels would not build on the course machines, so Mamba runs in plain PyTorch through mambapy. Same model, much slower (Lesson 5).
  • 141–142A selective state-space model: state size 16, a short convolution of 4, inner width 2 × d_model.
  • 146–153The model’s residual blocks are stepped through one by one, so the output after each block can be collected, exactly as mambapy’s own forward would compute it.

6.3The training loop

The task is next-token prediction, the same as a language model. The model reads a game and, at every position, predicts the move that comes next. In code that is one shift: the input is the game without its last token, the target is the game without its first.

  • 174–178The learning rate climbs linearly for 200 warm-up steps, then falls along a cosine to zero at step 5,000. It always uses the full budget as the end point, so a 300-step throughput run trains on the same schedule.
  • 184–185AdamW with weight decay 0.01, and cross-entropy that ignores target 0, the padding.
  • 190–191Micro-batching: Mamba large splits each batch of 256 into chunks of 64. Each chunk’s loss is divided by the number of chunks, and the gradients add up, so one optimizer step still sees all 256 games.
  • 198–199Each step draws 256 games at random, with replacement, from the loaded games.
  • 205–210The shift from the figure: read xc[:, :-1], score against xc[:, 1:], flattened over all positions.
  • 211–212Clip the gradient norm to 1.0, then step.
  • 200–215Wait for the GPU before and after each step, so the time per step is honest; that is what Lesson 5’s throughput numbers come from. The first 10 steps are dropped from the average (line 219).
  • 220–225The final loss is the mean of the last 20 steps.
A detail worth knowing

Because batches are drawn with replacement, a synthetic model draws about 63% of its 1.28 million games at least once, and about a quarter of them more than once. The comment in run_matrix.py (“so no game repeats within a run”) describes the intent of loading that many games, not exactly what sampling with replacement does. For the championship models, with only 110,005 games, every game is seen many times (Lesson 4).

6.4Evaluation: two numbers

  • 233–234Use the same chunk size as training, so big models fit, and build the validation games with legal moves (Lesson 3).
  • 238–243Next-token accuracy: how often the top prediction is the move the game actually played next.
  • 244Legal move rate: how often the top prediction is any legal move. This is D1’s number, computed here on validation games.

For the medium transformer trained on synthetic games with seed 0, next-token accuracy is 0.146 and the legal move rate 0.944. The gap is the point of the project: guessing the exact move is hard because random games pick among about 8.5 legal moves, while knowing which moves are legal is what a world model would give you. The legal move rate on these 1,000 validation games also decides whether the model is admitted to the study (Lesson 7).

8.1Why write the rules down first

The hypotheses are judged against numbers a team could tune after seeing results without ever meaning to: move the agreement threshold a little, drop a model that looks odd, summarize a score per layer instead of at the best layer. Each choice is defensible on its own, and together they let the data say whatever looks best. The preregistration removes those choices: it fixes them while only training records exist, so the later analysis is confirmatory (testing what was planned) rather than exploratory (finding what looks interesting).

After a tag, the document can change only through a dated amendment at its end, written before the results it affects exist, and the paper reports every amendment.

8.3The decision rules

H1: do the four diagnostics agree?

For each of the six pairs of diagnostics, Kendall’s tau measures how consistently the two rank the admitted models in the same order. Spearman’s rho is reported next to it, and Kendall’s W summarizes all four diagnostics at once.

Amendment 1: agreement through competence

Every diagnostic is likely to score a better-trained model higher. Across a zoo whose legal move rate runs from about 0.56 to 0.97, the four diagnostics could agree only because they all follow competence. So each pair is also reported with competence (the validation legal move rate) controlled, as a partial Kendall tau:

τ(x, y | c) = ( τ(x, y) − τ(x, c) · τ(y, c) ) / √( (1 − τ(x, c)²) · (1 − τ(y, c)²) )

A pair whose raw tau agrees but whose partial tau disagrees is reported as agreement through competence, and the partial result decides whether two diagnostics measure the same thing. Because D1 is nearly the legal move rate itself, a pair that includes D1 is marked not interpretable when tau(D1, competence) is 0.90 or more (A5). A sensitivity run repeats H1 on the admitted models with a legal move rate of at least 0.90 (A3).

H2: is the disagreement systematic?

Per model, disagreement is the standard deviation of its four rank percentiles, one per diagnostic. It is regressed on architecture, scale and distribution. Disagreement is systematic if at least one factor is significant at 0.05 after Holm correction and its effect is larger than the noise floor: how much each diagnostic’s score varies across the three seeds of the same configuration. Otherwise it is reported as consistent with noise.

H3: which diagnostic predicts fragility?

The outcome is the fragility suite’s mean drop in legal move rate (Lesson 14). Amendment 1 divides it by the model’s own in-distribution legal move rate, so a strong model is not penalized for having more to lose, and it makes D1 the reference rather than a competitor, because D1 and fragility are both legal move rates. The contest is among D2, D3 and D4: each one’s partial Spearman correlation with relative fragility, controlling for D1, plus a regression with architecture and scale. A diagnostic is the best predictor if its partial correlation is the strongest in the expected negative direction and the bootstrap intervals of its differences to the other two exclude 0. A diagnostic adds to D1 if its own interval excludes 0. If none does, the finding is that nothing predicts fragility beyond the legal move rate.

H4: do the findings generalize?

H1 to H3 are computed on Othello and navigation and written down before any interpreter model is scored. Then the same code runs on the interpreter. The findings generalize if every pair keeps its H1 category and the H3 winner (or the absence of one) stays the same.

  • 104–107logits: tokens in, next-move scores out, under no_grad. Tokens can be a NumPy array or a tensor; _to moves them to the model’s device as integers.
  • 109–114activations: the vector after every layer, stacked into one tensor. The assert catches an adapter that returns the wrong number of layers or the wrong width.
  • 116–126logits_edited: run the model, but at chosen layers replace the vector at one position per game with whatever a function returns, in layer order, so later layers see the edit. This is what the D4 causal check needs (Lesson 13).
  • 128–134logits_patched: the simplest edit, replacing one layer’s vectors with given ones.
  • 136–139Calling the model is the same as logits, so a ZooModel works anywhere a plain model(tokens) is expected, such as othello.legal_rate().
  • 184–190For zoo models both calls are one line, because every train.py class already has forward and layer_outputs (Lesson 6).
  • 196–209Edits use PyTorch forward hooks on the layer modules: each hook replaces the layer’s output before the next layer reads it. The LSTM returns a tuple, so only its first element (the output sequence) is edited. The hooks are always removed, even if the forward pass fails.

D1 · Next-token validity

D1 is the test most papers start and stop with: does the model only propose legal moves? It is the simplest of the four and the weakest, and the study includes it to measure exactly how much weaker. Everything it needs is already in Lesson 3.

About 10 minutes · Files: src/diagnostics/d1/next_token.py, src/docs/d1_next_token_validity.md · Owner: Viharika

10.1The idea

Take any prefix of a test game, say D3 C3 C4. The rules engine replays it and lists the legal next moves: C5 and E3. The model reads the same prefix and proposes its most likely next move. If that move is C5 or E3, the position counts as valid, even if the recorded game went on with the other one. If the model proposes anything else, say C3, which is already occupied, the position is invalid. D1 repeats this at every position of 1,000 test games.

The model does not need to guess the move the players chose; it only has to stay inside the rules. That is why D1 sits far above next-token accuracy (Lesson 6): about 0.94 against 0.15 for a medium transformer.

10.2The score

  • 96Find the model’s own training distribution: from models.csv for a zoo model, from its metadata for an anchor.
  • 97Load 1,000 test games of that distribution and build them with legal moves (Lesson 3).
  • 98The score: othello.legal_rate(), the share of positions where the top move is legal. The same function decided admission on validation games; here it runs on test games.
  • 99A second, sampled rate, kept in details only (section 10.3).
  • 100The number of positions scored: every position that has a recorded next move, about 58 per game.

10.3The second number: sampling instead of argmax

The top move hides how much probability the model puts on illegal moves. A model can rank a legal move first while still giving illegal moves 30% of its probability. So D1 also draws 10 moves at every position from the model’s full distribution (temperature 1.0, a fixed random seed) and reports the share of draws that are legal.

  • 68One seeded random generator for the whole run, so the same model always gets the same draws.
  • 71–75Turn the scores into probabilities and draw 10 moves per position, with replacement.
  • 78–82For the same positions legal_rate() scores, look up whether each drawn token is legal and count.

D2 · State equivalence

D1 asks whether each proposed move is legal. D2 asks something D1 cannot: does the model treat two histories that reach the same board the same way, and two histories that reach different boards differently, exactly where the boards differ? It is the state-equivalence test of Vafa et al. (2024), and this lesson takes it apart line by line.

About 22 minutes · Files: src/diagnostics/d2/state_equiv.py, src/diagnostics/d2/toy_check.py, src/docs/d2_state_equivalence.md · Owner: Venkatesh

11.1The idea: what a state is

In Othello, once you know the board and whose turn it is, the history no longer matters: every possible future is decided. The Myhill–Nerode theorem says the same thing for any system with a finite set of states (a deterministic finite automaton): two histories are the same state exactly when every continuation is equally allowed after both. A model with a real world model should respect that in both directions.

  • Compression.Two histories that reach the same state should get the same answer from the model. If they don’t, the model is still reacting to how it got there.
  • Distinction.Two histories that reach different states should get different answers, on exactly the moves that differ. If they don’t, the model has merged two boards.

11.2What the model “accepts”

A model outputs scores, not a set of moves, so D2 needs a rule for which moves the model accepts after a history h. It uses no threshold at all: if k moves are truly legal after h, the model’s accepted set A(h) is its k highest-scoring squares. The model gets exactly as many picks as there are legal moves, so nothing has to be tuned, and a perfect model’s picks are exactly the legal set.

11.3The two errors, worked by hand

Compression · same state pair

D3 C3 C4 and C4 C3 D3: legal C5, E3 after both, so k = 2. A hypothetical model accepts:

A(h)C5E3
A(g)C5F3

Accepted after only one of the two: E3 and F3, out of the 3 moves accepted after either.

compression error = |A(h) △ A(g)| ÷ |A(h) ∪ A(g)| = 2 ÷ 3

Distinction · different state pair

E6 D6 C5 (legal B4, F4, B6, F6) and F5 D6 C6 (legal F4, B6, F6). The boundary is B4: legal after the first only. A hypothetical model accepts:

A(h)B4F4B6F6
A(g)B4F4F6

B4 is accepted after both, so the model has not separated the boards where they differ.

distinction error = boundary moves not separated ÷ boundary moves = 1 ÷ 1

A boundary move that is legal only after h counts as separated when the model accepts it after h and not after g, and the mirror holds for moves legal only after g. Both errors are averaged over their pairs, and the score keeps the project’s rule that higher is better:

score = 1 − ( mean compression error + mean distinction error ) / 2

11.4Histories: every prefix, with its true state

  • 100–104Who moves next? legal_next() returns the other player’s moves if there are any, otherwise the mover’s own (Lesson 3). So whether its first square is legal for the other player tells which list it is, and therefore whether the other player has to pass.
  • 111Replay all games with legal moves (Lesson 3).
  • 114–123Every prefix of every game is a history. Positions with no legal move (game over) are left out, and a prefix shared by several games, such as a common opening, is kept once: a pair of identical move sequences says nothing about state equivalence.
  • 124–129The true state is the board plus the player to move, packed into bytes so that two equal states compare equal as dictionary keys.

11.5Sampling the pairs

All possible pairs are far too many to score, so both errors are estimated from samples: up to 2,000 pairs of each kind, drawn with seed 0. The pairs depend only on the games, never on the model, so every model of a distribution is judged on exactly the same pairs.

  • 143–147Same-state pairs: group the histories by state, then list every pair inside each group. These come from move orders that can be swapped, which is rarer than it sounds.
  • 149–151If there are more than 2,000, keep a uniform random sample of 2,000.
  • 162–166Different-state pairs are matched on length: a history length is drawn in proportion to how many pairs it offers, so every possible same-length pair is equally likely.
  • 169–176Draw two histories of that length, and draw again if their legal sets are equal or the pair was already taken.

11.6Accepted sets and the errors in code

  • 190–194One forward pass per game gives the scores for every prefix at once, because the models are causal: position t only sees moves 0 to t. Token 0 (padding) is dropped from the scores.
  • 195–199Ranking with argsort twice gives every square its rank; a square is accepted when its rank is below k, the number of legal moves. That is the top-k rule for all histories in one vectorized step.
  • 203–206Compression error per pair: moves accepted after exactly one history (^, exclusive or) over moves accepted after either (|).
  • 209–218Distinction error per pair: the boundary moves, legal after exactly one history, and the share of them the model fails to separate.
  • 264–273Same-state pairs occur only where move orders can be swapped, so 1,000 games may not give enough. If there are fewer than 500, add 1,000 test games at a time, up to 5,000. The synthetic anchor needed 4,000 games; the championship anchor 2,000.
  • 261–263, 275The prepared histories and pairs are cached per distribution, so scoring 27 models of one distribution replays the games once.

D3 · Inductive bias

D3 does not read the model’s answers or its insides. It watches how the model learns: give it a new job that depends on the true board and almost no examples, and see whether its training helps. This is the inductive-bias probe of Vafa et al. (2025), with its symbolic-regression arm.

About 20 minutes · Files: src/diagnostics/d3/inductive_bias.py, src/diagnostics/d3/toy_probe.py, src/docs/d3_inductive_bias_probe.md · Owner: Nikhil

12.1The idea

A model trained only on move lists becomes good at next-move prediction. Did it learn Othello, or only which move tends to follow which? From the outside the two look the same. So D3 gives the model a job it has never done, with only 64 labelled examples to learn it from. If the model already tracks the board, 64 examples are enough to learn what the question means. If it only memorized move patterns, they are not, because the answer depends on a board it does not have.

A second model with the same architecture and size, but random weights, gets the same 64 examples. It shows what 64 examples are worth on their own. The difference between the two is the model’s inductive bias: what its training makes easy to learn. Vafa et al. found that models trained on planetary orbits predicted trajectories well, yet once adapted to a new physics task behaved as if they had learned a force law that makes no physical sense.

The toy version first

toy_probe.py runs the same idea in seconds on the smallest world with the same shape: a walker on a line of six positions with a wall at each end. Pretrained on next-move prediction, then adapted on 16 walks to answer “where is the walker now?”, the pretrained model beat its random twin on all five seeds, by 0.27 on average, but the gap ranged from 0.12 to 0.33 across seeds. One seed is not enough to rank models, which is why the real protocol uses three.

12.2The four tasks

Each task is a yes-or-no question about one square right after a move: “is square X mine?”, where mine means the disc belongs to the player who just moved (the mine_theirs board from Lesson 3). The squares are C4, F5, C3 and F6. Between about 41% and 55% of the answers are yes, depending on the square and the distribution, so the tasks are close to balanced.

Why not “is square X occupied?”

It was considered and rejected. On 2,000 synthetic validation games, whether a square is occupied equals whether its token appears in the move list in 100% of cases, so it can be answered without any board at all (Lesson 2). Whose disc it is depends on every flip since, and cannot be read off the move list.

12.3The protocol

Balanced accuracy is the mean of the hit rate on “mine” and the hit rate on “not mine”. A model that always answers the more common class scores 0.5, not the 0.55 to 0.59 plain accuracy would give it, so a lazy answer earns nothing.

Why these learning rates

They were chosen on the synthetic Othello-GPT only, never on a zoo model (Amendment 1, A7). Of the four settings tried, a body rate of 1e-4 gave the largest gap (0.140). A body rate of 1e-5 was also rejected for a second reason: it leaves the model almost frozen, so D3 would become a linear probe on the last layer, close to D4 by construction, and their agreement under H1 would be partly built in.

12.4The code

  • 135–138Build the games (Lesson 3) and pick one random real position per game, with a fixed seed, so the adaptation and test examples never change between models.
  • 140–141Read the mine/theirs board at that position and turn it into four 0/1 labels, one per task square.
  • 197–203A fresh 2-way head, and AdamW with two learning rates: 1e-3 for the head, 1e-4 for the rest of the model. Training mode is needed because cuDNN’s LSTM only computes gradients in it; there is no dropout to switch on.
  • 209–215300 steps, each on 16 of the 64 examples drawn with replacement. last_layer() returns the vector after the last layer with gradients on, for any architecture, and the head reads it at the example’s position.
  • 218–225Score all 1,000 test positions, and keep the margin, logit(mine) − logit(not mine), for the symbolic-regression arm.
  • 405One random-weights twin per seed, shared by the four tasks: build_model() for a zoo model, a fresh 8-layer TransformerLens model for an anchor.
  • 407–410Both are adapted as deep copies, so neither the trained model nor the twin changes between tasks, and every other diagnostic still sees the original weights.

What D3 measures, and what it does not

A model whose last layer already holds the true board reaches only about 0.8 balanced accuracy from 64 examples, because many features can fit 64 points. So D3 measures how much the pretrained model helps, not how close it gets to a perfect answer. The paper states this limitation.

12.6The symbolic-regression arm

Vafa et al. also asked which rule an adapted model has learned. After every adaptation, D3 runs PySR, a symbolic-regression search, to find a short formula that reproduces the adapted model’s margin on the 1,000 test positions from the 64 true squares (+1 mine, −1 theirs, 0 empty). The search uses only +, − and ×, at most 15 nodes, the 10 most relevant squares, 40 iterations, deterministic, with the adaptation seed as its random seed. Then it reads the formula square by square:

  • 314–320For every square j, set it to mine, theirs and empty on all test boards and compare the formula’s outputs. Contrast: how much the formula tells mine from theirs on j. Occupancy effect: how much it reacts to j being occupied at all.
  • 323–325Law recovered: the task’s own square has the largest contrast, mine raises the margin, and the formula’s sign beats chance against the true answer.

A formula like a × sq_C4 × sq_C4 + b gives the same value for mine (+1) and theirs (−1): it only notices that C4 is occupied. It has zero contrast, so it never counts as recovered. It is flagged as the occupancy shortcut instead. Two real formulas the synthetic anchor’s adapted models produced for “is C4 mine?”:

sq_C4 - sq_E5                                # seeds 1 and 2: mine on C4 raises the answer; the law is recovered
-6.1055055 - (sq_C4 * (-5.1848264 * sq_C4))  # seed 0: grows with sq_C4², i.e. "C4 is occupied": the shortcut
AnchorLaw recovered: pretrained · randomOccupancy shortcut: pretrained · random
Othello-GPT synthetic2/12 · 1/127/12 · 1/12

The short formulas almost never recover the “is X mine?” law. What they find instead, in about half the searches and almost never for the random twins, is the occupancy shortcut: once adapted, the pretrained models’ answers largely follow whether the square is occupied. Part of D3’s pretrained advantage may therefore come from occupancy, which the move list gives away. The D3 score is unchanged; the shortcut rate is reported next to it for every model, so the analysis can show how much of D3 it explains. Stability across the three seeds (the overlap of the squares each formula uses) is reported too, because the search is stochastic.

D4 · Representation probing

D4 opens the model up. If it keeps a picture of the board inside, a simple classifier should be able to read the board from its activations, and editing that picture should change its moves. Two checks keep the reading honest: a control task, and the causal edit.

13.1The idea, and the number it was checked against

The model only ever reads move tokens. 13.2Data, activations and the probe

  • Three sets of games, never mixed.From 11,000 validation games of the model’s own distribution, the first 10,000 fit the probes and the last 1,000 choose the layer. 1,000 test games give the score, so the test games never influence any choice.
  • Every layer, every position.The vector after each block (transformer, Mamba) or each LSTM layer, at every real position of every game.
  • Standardized first.Each activation feature is shifted and scaled by its mean and spread over the fitting games. LSTM hidden states lie between −1 and 1 while residual streams are much larger, so without this one learning rate would be unfair to some architectures. Checked on a model whose layer holds the true board: the probe reads it at 0.9999.
  • One linear map per layer.From the width of the layer to 64 squares × 3 classes, trained with cross-entropy and AdamW (learning rate 1e-3, weight decay 0.01) for 2 epochs, one step per 1,024 positions: about 1,100 steps.
  • 219–220Activations for 256 games at a time, computed under no_grad: the model is only read, never trained.
  • 221–223The real labels from mine_theirs, the control labels (section 13.3), and the standardized vectors, all at the real positions only.
  • 224–237Shuffle the positions and take steps of 1,024. Each step trains, for every layer, the real probe on the real labels and the control probe on the control labels, from the same vectors. The MLP probes (section 13.6) have their own optimizer, so adding them left the linear probes, and the score, exactly as before.

13.3The control task: how much can a probe score by memorizing?

A probe with enough capacity can learn things the model does not represent in any useful way, simply by memorizing. Hewitt and Liang (2019) proposed a control: give the probe labels that have no link to the board, and see how well it does anyway. The real probe’s accuracy minus the control probe’s accuracy is the selectivity, the part of the reading that memorizing cannot explain.

Real labels · from the board

Two games both have E3 played as move 4. Their boards differ, so the real labels differ: the probe must read the board out of the vector to get them right.

Control labels · from the type only

A position’s type is (square just played, position in the game): 60 × 59 = 3,540 types. Each type gets one fixed random label per square, drawn from that square’s real mix of classes. Both games above get the same control labels, so a control probe can only score by recognizing types.

  • 126–129The type of every position: token of the square just played × 59 + position.
  • 132–135How often each square is empty, mine or theirs in the fitting games.
  • 138–144One uniform random number per type and square, turned into a class by that square’s cumulative frequencies, with seed 0: the control labels match the real class mix, but carry no information about any particular board.

13.6The causal check: does the model use what the probe reads?

A board that can be read from the activations is not necessarily a board the model uses. The probe might pick up a by-product. Li et al. (2023) settled this for Othello-GPT by editing its internal board and watching its moves follow. D4 does the same on every model, against a control edit of the same size.

  • 350–353Work in the standardized space, with a step length of 0.05 × √width, so a step means the same for every architecture.
  • 356–361Stop moving a case as soon as the probe reads the whole edited board and gives the flipped square’s new class at least 0.99. Edits stay as small as that allows.
  • 362–367Otherwise take one step down the gradient of the probe’s loss for the edited board, normalized to unit length, and only for the cases not yet done.

The synthetic Othello-GPT is the positive control, because the published work already showed its board is causal: editing it moves boundary accuracy from 0.18 to 0.87. The championship model’s board is readable (selectivity 0.27) but editing it barely beats a random push, so it is labelled decodable but not causal. H3 reports such models separately and tests whether the label predicts fragility beyond the selectivity score.

Why edit from the middle layer onward? The setting was chosen on the anchors only, as the one with the largest causal score on the positive control. Editing only the best layer (6 of 8) comes too late: later layers still attend to earlier positions that hold the unedited board, and the synthetic model builds its board around layer 4. Editing from layer 0 adds noise where no board is held yet. The 0.20 pass mark was written down before that comparison was run and not changed after it.

The fragility suite

H3 asks which diagnostic best predicts when a model breaks on situations that are related to its training but shifted. Something has to define “breaks”, and it had to be defined before any diagnostic score existed. That is the fragility suite: frozen on 6 October with the tag fragility-v1.

About 15 minutes · Files: src/fragility/othello.py, src/docs/fragility_suite.md, src/tests/test_othello_fragility.py

14.1Same rules, shifted situations

Every variant keeps the Othello rules exactly as they are and changes only which positions the model is asked about, so the right answer always comes from othello.py. Nothing in the suite retrains or adapts the model. The proposal had listed “altered legal move rules” too, but a model can only follow a changed rule after being adapted to it, and adaptation is what D3 measures; using it here would make H3 partly “does D3 predict D3”. The team dropped it on 5 October, before freezing the suite.

14.2Symmetry: the same game, relabelled

For a random-game model this is barely a shift, because random games open in all four directions equally. For a championship model it is a real one: the archive records every game in one orientation, so all 110,005 of its training games open with F5 (Lesson 4), and a rotated game starts with a move it has never seen first.

14.3After a pass

A position counts when the next recorded move is made by the same player who made this one: the opponent had to pass. A model that only learned “the players take turns” proposes a move for the wrong player there. Passes are not that rare (about a third of random games and 58% of championship games contain one), but they are a small share of positions.

14.4Detours: pushing the model off its line

  • 194–195One forward pass for every game still alive, reading only the last position’s probabilities.
  • 197–203Passes and game ends follow the rules: no legal move means a pass, and if neither player can move the game is over, and counts as completed.
  • 205–209An illegal top move ends that game as a failure.
  • 212–218With probability p, and only when there is a choice, the move is swapped: for a random other legal move, or for the one the model gives the lowest probability.

14.5One number per model

  • 271Every static variant’s drop: the in-distribution legal move rate minus the variant’s.
  • 279–283Every detour drop: the undisturbed completion rate (p = 0) minus the completion rate with detours, for each mode and each p.
  • 291fragility = the mean of all the drops. Higher means more fragile. The drops are kept one by one too, so H2 can ask which shifts each diagnostic sees.
A drop needs something to drop from

An untrained model scores a fragility near zero (0.02 to 0.03 in a smoke run): it is equally bad everywhere and has nothing to lose. That is why the in-distribution rate is always reported next to fragility, why H3 uses only admitted models, and why Amendment 1 divides fragility by the in-distribution rate (relative fragility) before asking which diagnostic predicts it (Lesson 8).

14.6Frozen, and how to run it

Everything the suite does is set by one dictionary, SUITE (1,000 test games per variant, data seed 0, the symmetries, the detour settings), and suite_hash() hashes it together with the version name. The freeze test in Lesson 8 fails if the hash ever differs from 644671bfb322. A different suite has to be a new version with a new tag, and every result file records which suite and hash produced it.

python src/fragility/othello.py --model outputs/zoo/othello_transformer_small_synthetic_s0/model.pt \

The tests check the suite against two models whose answers are known: a perfect world model (replays the rules, proposes only legal moves) must score zero on every variant, and a broken one (always the same square) must fail. They also check that each symmetry keeps the start board, that the after-pass positions are real passes, and that the same seed gives the same detours.

15.5Adding a fifth diagnostic

The proposal promises a plug-in interface: any future world-model test can be compared with the four on identical ground truth. With everything in this course, that means:

  1. Write a module with DIAGNOSTIC, METHOD and score(model, split, n_games, data_seed, **config) that returns itf.result_for(...), takes games and truth from othello.py, fits only on val and scores on test (Lesson 9).
  2. Give it a name in run_matrix.py (DIAGNOSTICS and DIAG_NAMES), which gives it a result folder and lets results.validate() accept it. That adds rows to the frozen plan, so it needs an amendment.
  3. Test it on fake models with known answers, the way the four existing ones are tested: an oracle, a constant model, a planted board.
  4. Write its protocol into a dated preregistration amendment and tag it, before it scores a single zoo model, and give its script the same tag check (Lesson 8).
