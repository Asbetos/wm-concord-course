The last stage turns 324 Othello result files into answers. This lesson covers the master table that joins them, what the H1–H4 analysis has to compute (that code is still to be written), the Streamlit demo, and the tests and CI that keep all of it honest. It ends with how a fifth diagnostic would plug in.

15.1The master table

  • 246–247Read the plan (models.csv) and every result file of every diagnostic, validating each one (Lesson 9).
  • 249–253One row per planned model, optionally for one domain: its model fields and whether it is held out.
  • 254–257For each diagnostic, its score and status. A run with no result file is marked missing, which is different from failed or skipped: those come with a written reason.
  • 262–265The missing report lists, per diagnostic, every planned run with neither a score nor a reason. The rule the project follows is zero silent gaps.

The master table holds the four diagnostic scores and nothing else. The analysis joins two more sources to it: competence and admission from src/docs/zoo_registry.csv (Lesson 7), and fragility from results/fragility/ (Lesson 14).

15.2From the table to H1–H4

The analysis code is the one stage the repository does not have yet. Its job is fully specified by the preregistration (Lesson 8), so it can be written without any new decisions. This is what it has to compute, per domain, on the admitted zoo models only (never the anchors):

A checklist for whoever writes it

Filter to admitted models of one domain; keep seeds as separate models; report raw and competence-controlled H1 side by side, with the “agreement through competence” and “not interpretable” labels (A1, A5); run the 0.90 sensitivity analysis only if at least 10 models qualify (A3); use relative fragility for H3, with raw fragility as a secondary result (A2); report D4’s “decodable but not causal” models separately and test whether the label adds anything beyond selectivity; and report how many models were not admitted, per architecture and scale.

15.4Tests and CI

Most tests run on fake models whose correct answers are known in advance, so they need no data, no checkpoints and no GPU. Tests that do need the real data or the Othello-GPT weights skip themselves when the files are missing.

FileWhat it pins down
test_othello_domain.pyStart board, first moves, tokens round trip, random games replay legally, build() shapes and labels, illegal games dropped
test_othello_distributions.pyThe WTHOR reader on hand-made files, cleaning, the cached split, the three distributions and the mixed ratio
test_othello_fragility.pyThe freeze hash, symmetries keep the start board, real passes, a perfect model scores 0 and a broken one fails, detours are reproducible
test_interface.py, test_results.py, test_registry.pyShapes, every architecture’s activations, a crash becomes a failed result, schema validation, the master table and missing report, admission, the checkpoint hash check
test_d1_next_token.pyAn oracle scores 1, a model that only proposes padding scores 0, positions match legal_rate()
test_d2_state_equiv.pyHistories and pairs, the pass rule, errors on hand-made sets, oracle / constant / noise, too few pairs, adding games
test_d3_inductive_bias.pyA model whose last layer is the board beats its random twin, identical models give no gap, the original weights never change, the symbolic arm (with a stand-in for PySR on CI)
test_d4_representation_probe.pyA planted board is read at the right layer and beats the control, a model that uses its board is causal and one that only stores it is not, edits run in layer order on every architecture

GitHub Actions runs the whole suite on every pull request and every push to main, with CPU-only PyTorch and without PySR’s Julia backend. Locally: python -m pytest src/tests -q.

15.5Adding a fifth diagnostic

The proposal promises a plug-in interface: any future world-model test can be compared with the four on identical ground truth. With everything in this course, that means:

  1. Write a module with DIAGNOSTIC, METHOD and score(model, split, n_games, data_seed, **config) that returns itf.result_for(...), takes games and truth from othello.py, fits only on val and scores on test (Lesson 9).
  2. Give it a name in run_matrix.py (DIAGNOSTICS and DIAG_NAMES), which gives it a result folder and lets results.validate() accept it. That adds rows to the frozen plan, so it needs an amendment.
  3. Test it on fake models with known answers, the way the four existing ones are tested: an oracle, a constant model, a planted board.
  4. Write its protocol into a dated preregistration amendment and tag it, before it scores a single zoo model, and give its script the same tag check (Lesson 8).

That is the whole repository. Every lesson’s code excerpts are generated from the project at build time, so after the code changes, rebuilding this course keeps every excerpt and line number in step.
